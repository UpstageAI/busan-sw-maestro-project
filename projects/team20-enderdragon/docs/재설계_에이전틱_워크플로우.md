# 에이전틱 워크플로우 재설계 — 설계서

> 프로젝트: **[엔더드래곤]** · 이슈: [#31](https://github.com/qlqlrh/asm-team20-ai-study/issues/31)
> 인앱(Fabric) 연동을 기준으로, 현행 5노드 선형 체인을 **상태 인지 · 결정론 검증 · 멀티턴 진행관리**가 가능한 실용 에이전틱 워크플로우로 재설계한다.
>
> 📌 설계 기준(North Star)은 [스펙문서.md](스펙문서.md), 현행 구현은 [기술_문서.md](기술_문서.md). 이 문서는 **재설계의 확정안**을 담는다.

---

## 1. 배경 & 방향 전환

- **인앱 기준 전환**: 마크 인앱(Fabric 플러그인) 연동이 성공하여 **인앱 동작이 기준**이 되었다. 비전/이미지 분석은 드롭한다 — 인앱이 인벤토리 등 게임 상태를 API로 직접 수집하므로 스크린샷이 불필요하다. (기획서의 "웹 우선 → 플러그인 후순위" 프레이밍 폐기)
- **재설계 이유**: 현행은 `analyze → clarify → retrieve → respond`의 **RAG+되묻기+응답 선형 체인**으로, 진짜 agentic이 아니다. 다음이 비어 있다.
  - 목표 분석/선행조건/부족자원/하위목표/실행계획 분해 (planning)
  - 계획의 **결정론적 검증** (제작 가능 여부를 LLM 추측이 아니라 규칙으로)
  - **턴 간 진척도 유지·reconcile** (이전 계획 대비 전진 vs 재계획)
- **설계 원칙**: 11노드 풀분해(레이턴시·환각 누적)와 단일 응답(비agentic) 사이의 **중간 분해**. "agentic"의 본질(상태 인지 → 근거 검색 → 결정론 검증 → 적응적 재계획 → 턴 간 상태 유지)을 과도한 LLM 홉 없이 달성한다.

## 2. 현행 구현 실태 (main `11732fd` 기준)

- **5노드**: `analyze`(도메인/키워드/intent) → `route_by_domain` → minecraft면 `clarify`(되묻기 판단) → `route_by_clarification`(ask|retrieve) → `ask`(되묻기 반환)→END / `retrieve`(Qdrant+확정사실)→`respond`(코칭+TODO, SSE)→END. general/out_of_scope는 곧장 respond.
- **인앱 수집**: 인벤토리만(아이템ID+개수, 41슬롯). 시간·체력·좌표 등은 미수집.
- **결정론 데이터**: `knowledge/minecraft_facts.py`에 RECIPES(17, 사람용 문자열)·MINING_REQ·PICKAXE_LEVEL·ACQUIRE·ALIASES·`item_ko()`. **RDB 아님**(Python).
- **상태 영속화**: 세션/메시지만(MySQL). 진척도·현재목표·직전계획 저장 안 함.
- **가드레일**: `general` 도메인이 비마크 질문을 일반 LLM처럼 답함(문제 — §7).
- LLM=solar-pro2, respond만 토큰 스트리밍.

## 3. 목표 워크플로우

### 3.0 목표 클래스 — 워크플로우가 다루는 범위
초보 코칭은 **제작에 국한되지 않는다.** `resolve_goal`이 사용자 목표를 아래 클래스로 분류하고, 클래스에 따라 처리 경로가 갈린다. **결정론 엔진(`compute_gap`)·`verify`는 '제작/자원' 목표에만 적용**되고, 나머지는 game_state + RAG + LLM 추론으로 코칭한다.

| 클래스 | 예 | 주 처리 경로 |
|---|---|---|
| 🔨 제작/자원 | "철 곡괭이 만들래", "침대 만들고 싶어" | retrieve(facts) → plan → **verify(compute_gap)** → coach |
| 🌙 생존/상황 | "밤 오는데 집 없어", "배고파 죽겠어" | game_state(시간·체력) + RAG → plan(LLM) → coach · *compute_gap 미적용* |
| 🧭 탐험/길찾기 | "철 어디서 캐?", "집에 어떻게 가?" | game_state(좌표) + RAG → coach |
| 🤔 막연형 | "이제 뭐 해야 해?" | resolve_goal이 상태 보고 **다음 목표 제안** → 제안된 목표의 클래스로 처리 |

> `compute_gap`은 '제작 가능 목표'를 결정론으로 검증하는 **한 도구일 뿐, 코치 전체가 아니다.** 생존·탐험·막연형은 게임 상태와 위키 근거로 코칭한다. 어느 클래스든 공통으로 game_state·세션 진척도를 활용한다. (크래프팅 편향 방지)

```
START
└→ load_state        [결정론]   세션 상태 로드(현재목표·진행중 plan·완료 subgoal·직전 인벤) + 최근 대화
   analyze           [LLM]      도메인/intent + turn_type(new_goal·progress_update·follow_up·help_request)
   route_by_domain   [분기]     minecraft / smalltalk / rejected
     ├ smalltalk → smalltalk_reply → END
     ├ rejected  → reject_reply    → END   (비마크 거절)
     └ minecraft ↓
   resolve_goal      [LLM]      명시 목표 추출·정규화 OR 막연형이면 상태 보고 다음 목표 제안
   check_goal_clarity[조건부]   목표가 모호할 때만 되묻기(가드: inventory_connected·prev_was_clarification)
     ├ needs_more_info → ask_clarification → END
     └ ready ↓
   retrieve          [결정론]   facts(인메모리) + Qdrant RAG, 해결된 목표 기준
   plan              [LLM 1콜]  선행조건+부족자원+하위목표+실행순서를 구조화 Plan으로
   verify            [결정론]   facts로 검증: 레시피 존재·채굴티어·부족자원 산수. 불가→선행조건 주입(대체경로)
   reconcile         [결정론+경]직전 plan·인벤 델타와 대조 → 다음 subgoal 전진 vs 재계획
   coach_response    [LLM 스트림]검증된 plan을 초보 코칭 + 짧은 TODO + 제작법 격자로
   persist_state     [결정론]   갱신된 목표·plan·진척도 저장(coaching_state)
   → END
```

LLM 호출 ≈ 4~5(analyze·resolve_goal·plan·coach + 선택 reconcile). 사용자 체감은 `coach_response` 스트리밍이 가린다.

### 클린 그래프 원칙 (코치 피드백)
라우트 함수 반환값 = **목적지 노드명과 일치하는 의미 이름**. 노드명은 행동을 드러내는 동사형. conditional_edges 매핑 dict가 한눈에 읽히게. (PR #29에서 route_by_domain은 이미 정리됨 — 같은 기준 유지)

## 4. 노드별 사양

| 노드 | LLM | 입력 → 출력 | 핵심 로직 |
|---|---|---|---|
| load_state | ❌ | thread_id·요청 inventory/game_state → prior_goal·prior_plan·completed·last_inventory·history | DB에서 CoachingState + 최근 대화 로드. 신규세션이면 빈 상태 |
| analyze | ✅ | query·history·game_state → domain·intent·keywords·**turn_type** | turn_type이 resolve_goal·reconcile을 좌우. temp 0 |
| route_by_domain | 분기 | domain → minecraft/smalltalk/rejected | 비마크는 거절·잡담 경로(§7) |
| resolve_goal | ✅ | query·turn_type·prior_goal·game_state·inventory → resolved_goal·goal_key·**goal_class**·source | 명시목표 정규화(ALIASES) + **목표 클래스 분류(제작/생존/탐험/막연형, §3.0)**. 막연형은 **상태 보고 목표 제안**(밤→첫 밤 넘기기). progress/follow_up은 prior_goal 승계 |
| check_goal_clarity | ⚠️ | resolved_goal·inventory_connected·prev_was_clarification → need_clarification | **목표가 모호**할 때만 LLM 되묻기. 가드 유지. 데이터 유무 체크 아님(인앱은 항상 인벤 있음) |
| retrieve | ❌ | resolved_goal·keywords·inventory → structured_facts·search_results | facts 인메모리 + Qdrant. 목표 기준 |
| plan | ✅ | goal·facts·search·inventory·game_state → **Plan** | Plan{requirements[], resource_gap[], subgoals[{id,title}], actions[{step,subgoal_id,detail}]}. facts 근거. temp 0.2 |
| verify | ❌ | Plan·inventory·facts → verified·blocked_steps·교정 gap·prerequisites | **제작/자원 목표에만 적용**(생존·탐험은 건너뜀). facts로 결정론 검증, 부족자원 산수도 코드가 계산. 불가 스텝엔 선행조건 주입(=대체경로) |
| reconcile | ⚠️ | prior_plan·completed·last_inventory↔현 inventory·Plan → active_subgoal·갱신 plan | **인벤 델타로 완료 subgoal 자동 판정.** 진행이면 다음 subgoal로 전진 |
| coach_response | ✅ 스트림 | verified plan·active_subgoal·gap·prereq·recipe → 코칭·todos·recipe | 상태요약 + 다음 한 걸음 먼저 → 목표까지 TODO. 초보 눈높이·용어설명 |
| persist_state | ❌ | 갱신 plan·goal·완료·현 inventory → DB | coaching_state upsert + 메시지 저장 |

## 5. 상태 모델

### 5.1 인앱 수집 확장 (모드 → 백엔드)
`ChatRequest`에 `game_state` 추가. 모드에 `GameStateSnapshot` 신규.
```json
"game_state": {
  "time_of_day": "day|night",   // world.getTimeOfDay()%24000 (13000~23000=밤)
  "health": 18.0,                // getHealth() 0~20
  "hunger": 7,                   // getHungerManager().getFoodLevel() 0~20
  "dimension": "overworld|the_nether|the_end",
  "position": {"x":123,"y":64,"z":-45}
}
```
주변블록/몹 스캔은 범위 외.

### 5.2 AgentState 추가 필드
`game_state, turn_type, resolved_goal, goal_key, prior_goal, prior_plan, completed_subgoals, last_inventory, plan, verify_result, active_subgoal`

### 5.3 진척도 영속화 — `coaching_state` 테이블 (신규)
| 컬럼 | 타입 | 내용 |
|---|---|---|
| thread_id | PK, FK→chat_sessions | 세션 |
| state_json | JSON | `{current_goal, goal_key, plan:[{id,title,status}], completed:[id], last_inventory:[...]}` |
| updated_at | datetime | |

세션당 1행 upsert. 코드엔 Pydantic `CoachingState` 모델. MySQL은 **상태성 데이터(세션·coaching_state) 전용**.

## 6. 레시피 데이터

- **소스 = 게임 레시피 JSON 추출**: MC 1.21.1 jar(`data/minecraft/recipe/*.json`, shaped 634/shapeless 253/제련 등)을 일회성 오프라인 스크립트로 추출.
- **저장 = Python 인메모리(확정)**: `recipes.json` 생성 → import 시 dict 로드. 읽기전용·고정·소량·per-request 결정론 조회라 인메모리가 정답(시딩·DB왕복·DB의존 0). `structured_db_retriever` 계층은 유지, 뒷단만 메모리.
- **데이터 구조**:
  - `RECIPE_SHAPES[output]` = `{pattern:[3행], key:{문자→item_id}, result_count}` (3×3 배치, GUI 격자용)
  - `RECIPE_REQS[output]` = `{ingredient_id: count}` (verify 부족자원 계산용; pattern에서 파생)
- **커버리지 = 추출되는 전부.** 같은 추출로 `ITEM_ID_TO_KO`도 확장(없는 건 `item_ko()`가 영어 폴백).
- **제작법 표시**: 모드 GUI 3×3 아이콘 격자(주, `DrawContext.drawItem`) / 웹·폴백 ASCII 격자. 백엔드가 `ChatResponse.recipe`로 구조화 shape 전달=단일소스.
- **태그 처리**: 레시피가 `tag:`(예 `minecraft:planks`)를 쓰면 태그 JSON으로 대표 아이템/카테고리 해석.

## 7. 가드레일 정책 (수정)

현행 `general` 레인이 비마크 질문("제철과일")을 일반 LLM처럼 답하는 문제를 고친다. 기획서는 "비마크 → 관련 질문 요청 안내 후 종료".
- **minecraft** → 파이프라인 진행
- **smalltalk**(순수 인사) → 짧게 받고 마크로 유도 (유지할지는 선택)
- **그 외 전부** → `OUT_OF_SCOPE_RESPONSE`로 거절
- 분류 프롬프트를 강화해 애매한 건 out_of_scope로 민다.

## 8. RAG / 웹검색

- **RAG**: `retrieve` 노드에서 마크 질문에만. facts(결정론) + Qdrant(위키 텍스트). 결과는 `plan`(근거)·`coach_response`(인용)에 주입.
- **웹검색(옵션, 후순위)**: RAG 커버리지 부족 시 보강. `retrieve` 출력에 커버리지/신뢰도 신호를 두어, 나중에 `retrieve → (부족?) → web_search → 병합 → plan` 노드만 끼우면 되게 자리를 비워둔다.

## 10. 미결정 / 주의

- **한국어 아이템명**: jar에 ko_kr.json 없음(en_us만). 1차는 기존 `ITEM_ID_TO_KO` + `item_ko()` 영어 폴백으로 진행. 필요 시 Mojang 에셋에서 ko_kr 확보(후속).
- **태그 레시피 해석**: 대표 아이템 1개로 보일지, 카테고리("판자류")로 보일지 — 격자 렌더 시 확정.
- **plan/verify 경계**: 어디까지 LLM이 생성하고 어디부터 코드가 검증·교정하는지 §4 기준으로 구현 중 미세조정.
